## Important R1: creator key expiry during an admitted batch aborts the worker instead of cancelling the remaining work

Primary location: [db/034-recipient-assessments.sql:90](/tmp/lettercape-recipient-assessment-native/db/034-recipient-assessments.sql:90).

Related locations: [src/server/recipient-assessment-worker.ts:15](/tmp/lettercape-recipient-assessment-native/src/server/recipient-assessment-worker.ts:15), [src/server/recipient-assessment-worker.ts:24](/tmp/lettercape-recipient-assessment-native/src/server/recipient-assessment-worker.ts:24), [src/server/recipient-assessment-worker.ts:42](/tmp/lettercape-recipient-assessment-native/src/server/recipient-assessment-worker.ts:42), [scripts/recipient-assessment-worker.ts:14](/tmp/lettercape-recipient-assessment-native/scripts/recipient-assessment-worker.ts:14).

The worker admits the creator's active key and holds its row lock before processing. Expiration still advances with wall time while that lock is held. Every observation insert independently requires `expires_at > clock_timestamp()` in the SQL guard. If the creator's otherwise-valid key expires after admission and before any later observation insert, the guard raises `RECIPIENT_OBSERVATION_INVALID`. That bypasses the worker's explicit cancellation branch, rejects the whole transaction, and reaches the CLI's `finally` without a catch/retry loop. The CLI closes its connection and exits. The assessment retains its earlier committed progress but remains queued/running, and other jobs on this worker stop progressing too.

Reproduction: create a keyed assessment with more than one captured member and a key expiring shortly; admit a batch while the key is valid; pause a wrapped fixture Tx immediately before its second `INSERT INTO recipient_observations` until the key expires; resume. Expect the insert error, transaction rollback, unchanged queued/running job status, and CLI termination. The current key test at `tests/recipient-assessments-db.test.ts:93` revokes before admission and cannot exercise this path.

Impact: a normal credential lifecycle event can stop the only explicitly supported local worker and leave durable work stalled until manual restart. Rollback protects evidence, but the specified between-batch cancellation/recovery behavior is not achieved.

Recommended correction: establish a coherent batch admission contract under the existing creator membership/key locks. An admitted preparation batch may finish, then the next batch should cancel if the key has expired; preserve the direct-SQL authority/fact guard rather than accepting a forgeable caller-supplied authorization flag. Alternatively, use a classified recoverable guard outcome and roll back/recheck/cancel through a bounded transaction recovery path. The root CLI also needs to survive classified transient batch failures. Add a deterministic restricted-role DB regression for expiry after admission and prove earlier observations remain intact and other jobs continue.

Cost: medium; coordinate worker admission and SQL guard behavior, then one focused expiry/recovery regression. No provider integration or migration of existing user data is required.

## Important R2: independent frequency-check timestamps can reject correct worker observations

Primary location: [db/034-recipient-assessments.sql:103](/tmp/lettercape-recipient-assessment-native/db/034-recipient-assessments.sql:103).

Related locations: [src/server/recipient-assessment-worker.ts:37](/tmp/lettercape-recipient-assessment-native/src/server/recipient-assessment-worker.ts:37), [db/034-recipient-assessments.sql:105](/tmp/lettercape-recipient-assessment-native/db/034-recipient-assessments.sql:105), [db/034-recipient-assessments.sql:106](/tmp/lettercape-recipient-assessment-native/db/034-recipient-assessments.sql:106), [scripts/recipient-assessment-worker.ts:14](/tmp/lettercape-recipient-assessment-native/scripts/recipient-assessment-worker.ts:14).

The worker calculates `frequency_limited` at one `clock_timestamp()` and passes the resulting reasons to a later INSERT. The guard recalculates frequency at another `clock_timestamp()` and demands identical reasons. An accepted reservation can cross its rolling-window cutoff between those two statements even though the contact lock prevents all contact/preference mutations. The worker's `FREQUENCY_LIMIT` fact is then rejected by the guard's later clear result. The error rolls back the batch and, with the current CLI, terminates the worker. This applies even with the database session timezone set to UTC.

Reproduction: give an otherwise-clear captured contact an accepted reservation whose daily/weekly/monthly cutoff is just ahead of the initial check; pause a wrapped fixture Tx between the checks SELECT and observation INSERT until after that cutoff. The SELECT returns true, the guard returns false, and line 105 raises `RECIPIENT_OBSERVATION_INVALID` despite no competing mutation. A retry can succeed once the cutoff has passed, but the current CLI performs no retry.

Impact: legitimate rolling-window expiration becomes an invalid-evidence error and can stall all queued work. It also means the persisted `observed_at` is not the exact instant used by the worker's supplied frequency fact.

Recommended correction: calculate and validate each observation's time-dependent facts against one authoritative database observation instant, or derive those facts once in the database insertion path. Deterministic SQL reproducer, which needs only a read-only SELECT after setting a session timezone:

```sql
SET TIME ZONE 'America/New_York';
WITH sample AS (
  SELECT timestamptz '2026-03-09 00:30:00-04' AS observed,
         timestamptz '2026-03-08 00:00:00-05' AS reserved
)
SELECT reserved > observed - 86400000 * interval '1 millisecond' AS shared_limited,
       reserved > observed - interval '1 day' AS guard_limited
FROM sample;
-- shared_limited = true; guard_limited = false
```

The elapsed-time cutoff is March 7 at 23:30 EST; the calendar-day cutoff is March 8 at 00:30 EST. An accepted reservation at March 8 at 00:00 EST lies between them. Use equivalent fixed instants around the current cutoff in a real fixture to show the worker INSERT rejection. The SELECT above was reviewed from documented operator semantics, not executed against a user database.

- **Competing admission:** A second tab obtains the lock after the first tab's durable write, observes its original, and rejects a different key/body. It can re-admit the same original for an idempotent retry. This prevents the earlier case in which both different keys passed verification and one recovery original disappeared.

- **UI uses only wrappers for recovery mutation:** The panel imports the atomic wrappers at `recipient-assessments.tsx:6`. - **Abort and lifecycle behavior:** The wrapper rejects already-aborted requests before queuing, passes the request signal to the lock manager, and checks abort again inside the granted callback (`recipient-assessment-recovery.ts:61-63`). An actor/configuration/unmount change invalidates that signal and generation through the existing fence. The new UI awaits do not allow a stale request to continue into POST or live state mutation.
- **Unsupported capability fails closed:** Missing lock support or a rejected lock request returns false without running the mutation (`:53-63`). Initialization, dispatch, and reload combine storage availability with lock availability (`panel :54, :91, :110, :143`).
