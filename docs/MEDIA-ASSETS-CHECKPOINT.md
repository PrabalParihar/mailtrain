## Important findings

### I1 — Expired leases permit another native chain without durable proof that the previous chain stopped

**Locations:** `db/031-media-assets.sql:57` (expired lease loop), `:60` (reset to pending), `:62` (global leased/blocked admission), `:84` (new lease); `src/server/media-supervisor.ts:136` (process-local reap), `:245` and `:275` (random process-local container names); `src/server/media-jobs.ts:81` and `src/server/media-worker.ts:111` (janitor before claim); `db/031-media-assets.sql:235` and `:252` (cleanup/forget accept expired leases); `tests/media-jobs-db.test.ts:99` (expiry directly followed by a new claim).

The handled abort/timeout path force-removes its known container, awaits confirmation and retains a blocked/accounted job if reap fails. That is sound while the owning worker remains alive. Recovery from an expired SQL lease uses a different rule: it clears the old lease and makes the job pending solely because time elapsed. A worker crash or lost database renewal does not imply that a Docker-daemon container, paused writer or its output mount ceased to exist. Runtime names and roots are generated only in process memory; SQL has no durable identity/reap barrier that a replacement worker can consult. The scheduler can therefore reclaim after30 seconds and start another scanner/decoder chain while the first native job can still run for60/90 seconds. This violates the explicitly promised one durable global chain and makes the resource ceiling dependent on worker survival.

The same missing writer-death fence affects staged cleanup: scheduler eligibility includes expired leases, so removal/acknowledgment can race the previous owner. Missing planned files deliberately keep reservations because a paused writer may install later, but finding and deleting an existing file is not proof that the old owner cannot write again. I count lease admission and this accounting/reap concern as **one issue**, not two independent vulnerabilities. Stale lease-token settlement correctly prevents old results becoming ready; it does not bound still-running physical work.

**Required correction:** persist planned runtime identities before any child launch and make expired ownership enter a durable reap/reconciliation barrier. The scheduler must confirm removal of every planned/running child and writer before reuse/cleanup accounting; if confirmation is unavailable, block admission and retain reservations. Runtime names must be deterministic/discoverable across worker death, and late launch/write must be fenced against reconciliation. An additive032 is appropriate if SQL state changes are needed. Merely extending the lease or declaring expiry equivalent to death is insufficient.

**Evidence limit:** the existing SQL recovery test explicitly treats accelerated expiry as sufficient to reclaim. It does not run an old surviving container while reclaiming. No new such probe was executed by this reviewer. Root should retain routine crash/reap qualification for its native pass.

### I2 — Asset availability is checked before rendering, but not at final cache settlement/response

**Locations:** `src/server/render-cache.ts:21` (verified bytes), `:22` and `:49` (cache reads), `:76` (awaited renderer), `:103` (cache insert); `src/server/assets.ts:161` and `:222` (short read transactions); `src/app/v1/[...path]/route.ts:338` and `:344` (ZIP construction/response); spec §7 current-takedown requirement.
