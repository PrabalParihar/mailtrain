## Findings

### F1 — Important — Recovery omits actor identity and can duplicate an acknowledged create after account switching

**Locations:** `src/ui/sender-form-recovery.ts:38` (form namespace), `:40` and `:46` (load/save), `:60`–`:65` (selection namespace); `src/ui/sender-domain.tsx:28`–`:35` (panel/controller identity), `:50` (editor identity), `:62` and `:96` (recovery/replay). The integration at `src/ui/app.tsx:519` supplies workspace and role but no actor. Relevant server behavior is `src/server/commands.ts:15` and `:20`–`:21`, and sender create at `src/server/sender-domain-route.ts:52`–`:57`.

**Trigger and reproduction:**

1. Actor A and actor B are both current Owners of one synthetic workspace.
2. In one browser context, A fills a new sender with `owned@actor.test` and saves it. The POST commits with 201; the fixture drops the acknowledgment, leaving the original body and key in recovery. There is one durable sender.
3. Change that browser's signed-in session to B and reload Delivery, retaining the same browser storage and workspace. B sees A's original form and enabled “Retry original sender command.”
4. B retries. Chromium verifies the exact original key and body are sent, yet the server commits another 201 create because its idempotency namespace correctly includes the current actor. PostgreSQL now contains two senders, one created by A and one by B.

**Evidence:** Independent owned Chromium + real local HTTP + PostgreSQL reproduction in `/tmp/lettercape-sender-reviewer-actor.cjs`; retained log `/tmp/lettercape-sender-reviewer-actor.log`. The probe asserts the first count is 1, exact body/key equality on replay, final count is 2, and distinct `created_by` values equal the two fixture actors. It passes exact workspace/session cleanup. Both actors have the same role, so adding only another role fence would not resolve this.

**User effect:** “Retry original” becomes a different actor's new mutation, creating duplicate sender setup and misattributing recovered work. It also exposes A's unapplied browser work to B. The same missing principal boundary affects pending DNS commands, selection, in-memory recovery, and delayed responses; the demonstrated acceptance failure is the duplicate create. Server tenant/role authorization is still enforced, and no provider action or send occurs, so this is Important rather than Critical.

**Repair:** Obtain a server-verified actor identifier, include it in sender form/selection/memory namespaces and controller/editor request context, and fence delayed responses when that identity changes. Bind pending recovery to that actor explicitly and refuse to replay legacy unbound or mismatched commands as another actor. Preserve A's recovery for A's return rather than silently deleting it or changing its command key. Do not widen server idempotency to workspace-only; separate principals must keep their own receipts.

**Native regression adaptation:** Run the retained fixture against the pinned source first with safe-behavior assertions (B cannot recover/retry A's command; durable count remains 1), observe RED, then apply the actor context fix and observe GREEN. Also verify same-actor lost acknowledgment still recovers its exact body/key, A can return to its preserved recovery, same-role actor changes discard old response installation, and legacy unbound commands cannot acquire the new actor's authority. No rereview is needed.
