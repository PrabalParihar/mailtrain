## Important findings

### I1 — A trustworthy remote ID is discarded when the create response has partial attributes

**Location:** `src/server/klaviyo-template-adapter.ts:20-24,48-49`.

**Condition:** POST returns 201 with a same-origin trusted response and valid `data.type = "template"` plus valid `data.id`, but the optional `attributes` object exists and is incomplete or has a schema mismatch. For example:

```json
{"data":{"id":"KNOWN_ID","type":"template","attributes":{"name":"Fixture"}}}
```

**Observed evidence:** A local invocation of `createAndVerifyKlaviyoTemplate` using a genuinely compiled artifact, the response above, and an injected fetcher produced:

```json
{"state":"outcome_unknown","code":"EXPORT_RESPONSE_UNTRUSTED","remote_id":null,"resource_url":null,"destination_url":null}
```

Call order was `["marker", "POST"]`; `persistRemoteId` was never called. The strict parse inside `receipt` rejects the incomplete attributes before returning the independently valid ID. Existing tests cover invalid IDs and fully valid known IDs, but not this partial-success shape.

**Impact:** A created remote object with a usable identity cannot be reconciled through the promised persist-ID-before-readback path. The primitive loses durable recovery information even though the acknowledgement provides it. There is no automatic POST retry in this implementation, which limits the immediate harm, but this violates the explicit requirement that only invalid success *without a trustworthy ID* is unknown and that known IDs survive verification failures. This is a present contract defect in the delivered primitive, even though it is unmounted.

**Correction:** Separate trusted identity/envelope admission from full attribute validation. After enforcing origin, resource type, ID syntax, and compatible self-link binding, persist that ID before any later attribute/readback validation. If the identity cannot be trusted, retain `outcome_unknown`; otherwise preserve it through `needs_attention` or a subsequent verified exact-ID GET. Add a covering case for a valid ID plus partial/malformed attributes, asserting persistence ordering, known-ID retention, and no second POST.

### I2 — Stored manifest corruption is accepted as an intact frozen artifact

**Location:** `src/domain/esp-export.ts:20-24`.

**Condition:** Frozen HTML, plaintext, spec, and artifact hash remain unchanged, but metadata in the stored manifest changes. The implementation regenerates a fresh manifest and checks its hash against the saved hash; it compares only the saved manifest's `spec` to the revision spec. The rest of the actual stored manifest is not compared.

**Observed evidence:** Starting from a real `compileEmail` result, independently replacing each stored manifest field below with `"CORRUPTED"` still allowed `compileKlaviyoArtifact` to return a downloadable preparation with the original source hash:

```text
manifest.renderer changed: accepted=true, sameSourceHash=true
manifest.mapping changed:  accepted=true, sameSourceHash=true
manifest.brand changed:    accepted=true, sameSourceHash=true
```

These were in-memory objects only; no saved revisions were modified. The underlying compiler computes its artifact hash over the complete manifest plus HTML and text (`src/domain/email.ts:290-301,383-386`), so the stored manifest is part of the claimed artifact identity.

**Impact:** The preparation presents an immutable-source integrity receipt for a saved artifact whose manifest no longer corresponds to that hash. This does not demonstrate arbitrary HTML injection: exact HTML/text equality and regenerated source hashes still protect those bytes. It does defeat the advertised fail-closed corruption/provenance check, including renderer and slot-mapping identity, and the stated policy that incompatible historical compiler artifacts must refuse preparation.

**Correction:** Compare the entire stored manifest to the regenerated manifest with an object-key-order-independent deep comparison or recursive canonical serialization that preserves array order and values; retain the exact HTML/text and regenerated hash checks. Reject missing, added, or altered manifest fields, including renderer, mapping, schema, brand, locale, and link-policy metadata. Keep the existing JSONB key-reordering success test and add corruption cases for non-spec manifest fields.

## Minor finding

### M1 — The destination download's generated response contract omits its actual media types and integrity headers

**Location:** `scripts/generate-api.ts:501-505,786`; generated `public/openapi.json:25312` and `sdk/schema.d.ts:26878`.

**Condition and evidence:** The new operation opts into generic `binary:true`. The resulting 200 response advertises `application/octet-stream` and only `X-Request-Id`/`X-Artifact-Hash`. The actual route (`src/server/esp-export-review.ts:27-30`) returns `text/html` or `text/plain` and supplies `X-Source-Artifact-Hash`, `X-Content-SHA256`, `X-Destination-Mapping`, `X-Remote-Export-Enabled`, and attachment/no-store/security headers. The operation description claims source/destination/per-format receipt binding but the generated schema does not describe those fields. The generic response description also mentions browser image/PDF simulations, which is inaccurate for this operation.

**Impact:** OpenAPI consumers cannot derive the exact media/receipt contract from the generated operation. The current SDK still exposes raw headers and handles binary bytes, so this does not break the reviewed editor path.

**Correction:** Give destination downloads their own response metadata in the generator, including the actual HTML/plaintext media types, relevant receipt headers and false remote-availability literal, and a destination-specific description. Regenerate OpenAPI/SDK and run the existing API drift check.
