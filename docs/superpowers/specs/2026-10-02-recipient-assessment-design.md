# Durable recipient assessment design

REQ-036 independent development slice. Full PRD baseline and all release gates remain binding. An assessment is historical preparation evidence, never a delivery attempt, approval, eligibility promise, send quota or frequency reservation.

POST /v1/campaigns/{id}/recipient-assessments strictly accepts expected_version (positive integer), expected_digest (64 lowercase hex), topic_id (UUID or null). Require current audience Owner/Admin authority, campaigns:write AND audience:read for API keys. The topic is an explicit assessment-only context; do not infer the legacy marketing string. GET campaign assessment history, GET /v1/recipient-assessments/{id}, GET its /observations, POST its /cancel. Reads require current audience authority and campaigns:read AND audience:read; cancellation campaigns:write AND audience:read. No generic operation entry is created, avoiding unrelated session operation leakage.

A keyed creation transaction locks current campaign, verifies CAS/digest and immutable configuration history, verifies frozen snapshot membership and source digest, validates selected topic belongs to tenant, then stores one immutable manifest and queued assessment. Require verified frozen audience snapshot; legacy implicit-all-contact drafts must first explicitly choose a snapshot. Maximum 10,000 sorted unique captured members. Store manifest contact IDs/metadata only, no recipient addresses. Durable PostgreSQL job row is the queue; Redis is not needed and loss cannot erase work. Poll a bounded batch under row FOR UPDATE SKIP LOCKED. Each transaction processes at most 100 captured members, commits append-only observations and progress together. Worker crash before commit rolls back, committed progress prevents duplicate observations. Unique (workspace,assessment,contact) dedupes logical members. New contacts never enter an existing assessment.

Current contact row locks serialize consent/preferences/suppression changes. SQL derives authoritative current facts/reasons and one observed_at, rather than accepting caller-supplied facts; frequency windows use fixed elapsed milliseconds. Creator admission checks wall time and holds membership/key locks; an admitted historical preparation batch may finish after key expiry, then the next batch cancels. Preserve captured exclusion separately; a captured excluded member remains excluded in this assessment. Evaluate current deletion, suppression, global confirmation, selected topic confirmation and existing shared rolling frequency ledger. Store current/captured locale and consent/preference versions, exact observation time and rule version. Frequency checks are read-only. Multiple reasons are retained; precedence deleted/missing -> captured exclusion -> suppression -> consent -> topic -> frequency. CHECKS_CLEAR means only inspected checks clear. Global blockers always include campaign approval, provider/sender connection, real-client preflight, send budget and locale mapping/policy; authorization_issued:false throughout.

Separate mutable job status/progress from immutable manifest/observations/history. Composite tenant foreign keys, forced RLS and revoked history updates/deletes protect storage. Creator current membership/API-key scopes rechecked between batches; revocation cancels pending work. Cancellation never removes observations. A new keyed assessment is required for a later observation; old history is not relabeled current.

UI is scoped by workspace/campaign/current actor and role, keyed original command is durable before dispatch using actor-bound local storage under an exclusive browser origin Web Lock. Mutation admission and matching-key clearing are atomic across tabs; unsupported locks refuse mutations while reads remain available. Storage failure refuses creation until durable recovery is available. Repeated clicks use synchronous busy guard; refresh/retry uses original key/body, never silently generates a second job. Async responses are fenced on unmount/actor/configuration identity. Strict schema responses, paged history and observations, truthful empty/loading/errors and mobile controls. Owner/Admin only; stale configuration reload required for a new command, original command replay remains possible. No provider submission transport or production bypass exists.

Runtime is explicitly local development worker only until production service identity/operations gates are qualified. CLI requires explicit workspace and actor and reads trusted environment normally; never copy private configuration. Independent worker use authorized by latest user instruction. Root owns integration/API/qualification, workers own disjoint domain, storage/runtime and UI files. Skill routine design approval does not add a pause: user explicitly authorized independent implementation. Future delivery/attempt engine remains undelivered; no simulated acceptance enters user data.
