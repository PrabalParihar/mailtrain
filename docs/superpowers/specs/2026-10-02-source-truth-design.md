## Design decisions and first vertical-slice boundary

### Exact source contract

Preserve exactly the accepted Unicode source string and its corresponding UTF-8 bytes, including BOM, CRLF/LF/CR, case, quotes, entities, whitespace, ordinary comments and unsupported/active markup. Do not normalize, prettify, trim, parse/serialize, strip BOM, decorate UTM or sanitize during canonical persistence. “Exact” refers to decoded accepted UTF-8 source, not arbitrary legacy encodings or original HTTP framing. Reject malformed UTF-8, unpaired UTF-16 surrogates and U+0000 before a transaction mutates data; PostgreSQL JSONB cannot losslessly represent these. UTF-8 BOM remains part of source (`TextDecoder` must be configured to retain it, e.g. fatal decoding with `ignoreBOM:true`). Do not normalize NFC/NFD.

An empty raw draft is valid editable source and can be durably saved; its artifact/preflight is incomplete with content/legal-slot blockers. This prevents deleting all text in the editor from becoming an inexplicable unsavable state. Source validation is distinct from deliverability; malformed HTML, active tags and unrepresentable VML can be saved as inert text without becoming approved artifacts.

Keep schema 1.0/1.1 for this change; they describe document/media shape. Introduce a separate server-owned source-storage profile (`exact-utf8-1`) and projection profiles (`raw-browser-1`, `raw-email-2`), rather than using a schema bump as a substitute for sanitizer/version provenance. No client can claim a source was safely projected or stored exactly merely by submitting a profile field.

### Sole authority and minimal migration

Add `db/032-email-source-contract.sql` (parent reserves the next number if another migration lands). Keep `emails.spec.raw_html` authoritative; do not add a mutable sanitized_html/source_text column that competes with it. Existing immutable `revisions.spec.raw_html` remains the exact frozen source for new revisions and the actually stored legacy source for old ones.

- Add server-owned `emails.raw_source_profile` and `revisions.raw_source_profile`: `NULL` for structured mode; `legacy-stored-1` for existing raw rows; `exact-utf8-1` for newly accepted raw writes/revisions. Use a trigger/check to keep mode/profile consistent. Legacy means “this is the source available in storage”; it does not falsely assert all old rows passed one sanitizer, because fixtures/API histories may differ.
- Add `email_source_provenance` append-only tenant rows: workspace/id/email ID, resulting doc_version, origin=`import|structured_fork|edit|restore|remix|locale`, parent/source revision ID where real, source SHA256/UTF-8 byte count/storage profile, principal/request/command identity and timestamp. Composite FKs, FORCE RLS and no runtime update/delete; payload contains hashes/IDs, never raw bodies or credentials. A normal source edit may create one small provenance record per durable accepted write; do not create a full duplicate source blob every five seconds.
- Add frozen revision source digest/byte count/profile in the **new manifest**, computed from the actual `spec.raw_html`. Do not rewrite old artifact/spec/manifest bytes or old hashes. A migration may backfill the separate profile column through migration privileges, but cannot invent/recover pre-sanitization originals.
- Restoring/remixing a legacy stored revision preserves exactly what is available, records the real origin/source revision and distinguishes its historical legacy provenance. A new write is exact preservation of those available bytes; it does not recover unknown prior source.

No retention/legal policy change is implied. Existing last-50 ordinary history and pinned revision requirements remain separate obligations; this slice does not build unlimited full-source autosave history or claim deletion/retention acceptance. Source text never enters general audit/event/analytics logs.

### Safe projections and honest VML/unsupported boundary

Introduce `projectRawHtml(source,context)` as a pure server function. It accepts source and verified asset metadata, returns explicit browser/email projections, diagnostics and their hashes, and never changes the supplied source/spec. Browser input is always the browser projection, never original source or email-specific conditional markup. Email/ZIP/ESP/send paths use only the delivery projection; source download is a separate text attachment.

Use existing pinned sanitize-html/parse5 with explicit allowlists; no eval, template compilation, dynamic JSX, network/fetch or code-executing plugin. Treat parsing/normalization as a transformation of the projection and report it. Source diagnostics use stable machine codes and bounded UTF-16 source ranges; display them through React text/pre elements, never `dangerouslySetInnerHTML` or unescaped tooltip HTML. Cap at 100 findings plus a `DIAGNOSTICS_TRUNCATED` count; this diagnostic cap never truncates source/output.

The **first increment** retains existing safe allowlist behavior for email output, now with specific diagnostics for active-content removal, style/tag/attribute removal, parser repair, external image/font/CSS resource blocking and conditional/VML unsupported fidelity. Conditional/VML source is preserved exactly in code/history/source download, but unsupported conditional content is not silently dropped from a claimed faithful deliverable. Set `delivery_status='blocked'` and a blocking `VML_FIDELITY_UNSUPPORTED`/`CONDITIONAL_FIDELITY_UNSUPPORTED` finding when meaningful unsupported content would be lost. A plain nonsemantic comment may be omitted in the projection with a nonblocking diagnostic; it remains exact in source.

This is a complete usable source-preservation vertical slice, not full TECH-032 VML acceptance. Subsequent preservation of allowed MSO/VML constructs is explicitly required for full GA and needs a narrow email-specific grammar, safety rules and actual Outlook evidence. Do not broadly set allowedTags/allowedAttributes to permit namespaces or preserve arbitrary comments to “pass VML.” Do not use regex sentinel replacement and reinsertion of arbitrary comment payloads. Parent may implement a proven narrow safe subset later, but this plan does not pretend that subset is already qualified.

No remote resources are fetched during import/projection. Exact remote URLs remain source/provenance; preview blocks them. Managed immutable asset markers are resolved only via the existing same-tenant registry and verified manifest, then injected into a transient browser projection as bounded data images. Unregistered/remote images are represented as unavailable in preview and are blocking for a new-profile distribution artifact whose image fidelity requires them. Do not invent asset IDs, proxy arbitrary URLs or publish private assets. Legacy artifacts retain their old disclosed behavior; a fresh compile uses the current profile and cannot reuse old safety evidence.

Legal/unsubscribe/primary CTA/locale/tracking/rights/publication checks still apply to final emitted output. A warning is not automatic export/approval authorization. Source persistence remains available despite these render blockers so users can repair the code. For UTM, derive validated email projection first, then apply current source-location-preserving UTM decoration once to that projection. Conditional/ambiguous remaining targets retain `UTM_LINK_UNSUPPORTED`; never silently omit tracking on hidden CTAs or bake decorated output back into source. Browser-safe form validation can show UTM render issues; source-only durable writes cannot be rejected merely because removed or unsupported content would fail a render-target policy.

### Explicit limits and transport

- `MAX_RAW_SOURCE_BYTES = 2 * 1024 * 1024` measured on UTF-8 bytes after strict decoding. Source length cap may be the same count as a quick UTF-16 upper bound, followed by actual TextEncoder/Buffer byte validation.
- In raw mode, non-source spec metadata/sections/registry must fit a separately measured 1 MiB JSON representation; structured mode retains its existing 1 MiB document contract. Inactive stale sections cannot bypass bounds or authorize assets, but remove them only through explicit mode-transition rules, not surprise source normalization.
- Existing generic JSON endpoints remain at 2 MiB. A specialized authenticated source/draft body reader can permit `MAX_SOURCE_COMMAND_JSON_BYTES = 13 * 1024 * 1024 + 64 * 1024` to cover worst-case JSON escaping of a 2 MiB source plus 1 MiB metadata/envelope. This is a route-specific transport ceiling, not permission for 13 MiB canonical HTML. Only source-bearing create/save/import/preview routes use it. Check source and metadata bounds after parse; over-limit requests never partially commit.
- Prefer a dedicated text import handler (`POST /v1/emails/:id/source-import`, `text/plain; charset=utf-8`) for actual 2 MiB file/paste import without base64. Keep legacy JSON `import-html` as a compatible wrapper, clearly bounded by its JSON envelope unless routed through the source-specific reader. Do not promise the full import size while retaining an inaccessible JSON envelope limit.
- Reject Content-Encoding, false/overstated size, invalid MIME/charset, absent required If-Match/idempotency and stream over-limit with precise codes. Actual streamed bytes are authoritative, not Content-Length. Read deadlines/cancellation and small per-process admission cap prevent stalled giant requests; no transaction is held throughout body reading.
- Parse/project at most 2 MiB source with a preflight count bound of 20,000 syntactic tags/comments and nesting depth 64, then verify actual parsed node bounds. If source is valid text but projection exceeds structural work bounds, preserve it and return `projection_status='unavailable'` with a blocking `RAW_PROJECTION_LIMIT`; never truncate it or mark the source save failed after commit. Each derived projection ≤4 MiB; if sanitizer/entity expansion exceeds that cap, return an explicit unavailable projection rather than partial output.
- Retain renderer input/bundle/resource budgets already established by the media slice. Raw-save/preview source limits do not silently raise worker-render budgets. Full-size raw files may be preservable even when a bounded PNG/PDF render is unavailable.

## Shared contracts to freeze before worker edits

New browser-safe `src/domain/email-source-contracts.ts` owns strict Zod schemas/types; no Node crypto/sanitizer imports in browser bundles. New browser-safe `src/domain/email-source-values.ts` owns `canonicalSpecString(spec:EmailSpec):string`, source representation/UTF-8-byte validation and shared constants. New server-only `src/domain/email-source-digest.ts` owns synchronous Node SHA256 helpers over those exact values. The client acknowledgement helper imports only the values/contracts files and uses `crypto.subtle.digest`, never the server digest module. Stable spec hashing sorts object keys recursively without changing string values/array order.

```ts
type SourceProfile = 'legacy-stored-1'|'exact-utf8-1';
type RawDiagnostic = {code:string;severity:'blocking'|'warning'|'info';
  start:number;end:number;message:string}; // UTF-16 offsets in exact original source
type RawProjection = {
  source_hash:string;source_bytes:number;
  browser_profile:'raw-browser-1';browser_html:string|null;browser_hash:string|null;
  email_profile:'raw-email-2';email_html:string|null;email_hash:string|null;
  delivery_status:'eligible_for_checks'|'blocked'|'unavailable';
  diagnostics:RawDiagnostic[];omitted_diagnostics:number;
};
type SaveReceipt = {
  receipt_version:1;workspace_id:string;email_id:string;
  request_base_version:number;saved_doc_version:number;
  command_id:string;spec_hash:string;
  source:{profile:SourceProfile;sha256:string;bytes:number}|null;
};
type SavedEmailResponse = {email:Doc;receipt:SaveReceipt};
type SaveContext = {workspace:string;actor:string;email:string;
  lifecycle:number;epoch:number;base_version:number;spec:EmailSpec;command_id:string};
```

Server receipt hash is computed from the actual committed parsed spec. Raw source hash is exact SHA256 of UTF-8 source, independently distinct from artifact hash. A receipt is acknowledgement metadata, not a bearer token or client-supplied proof. Ordinary `PATCH draft` replay uses existing principal/workspace/action-key namespace and a payload containing expected version and exact spec. Same command key/body returns the same committed response; changed body/base under same key is 409. Duplicate/lost response cannot create a second source write/version/history row. Replay rechecks current authority/resource existence; it does not bypass revocation.

`validateSaveAcknowledgement(context,response)` must validate identity, strict response shape, `saved_doc_version === base_version + 1`, matching receipt/doc version, matching exact source string, canonical full-spec digest and returned profile/hash/bytes. It cannot simply trust receipt hash without recomputing against returned/submitted source. Use exact source equality; canonical sorting avoids meaningless object-key-order mismatches. The result is either a verified response or a typed non-acknowledgement; no partial ack/version adoption on failure.

## Costs, material decisions and deliberately deferred alternatives

No provider fee, account, infrastructure provisioning or paid commitment is needed for this slice. Existing open-source dependencies suffice. Measure parser/compiler CPU, bounded request/source/preview/receipt memory, raw source retained per immutable revision, DB source-provenance growth and browser local recovery size. Up to 2 MiB source plus 1 MiB metadata and JSON escape expansion to the explicit 13 MiB + 64 KiB command bound is a worst input ceiling, not typical memory usage or a priced customer allowance. No unbounded source autosave blob history is introduced.

Routine choices already decided here: keep canonical raw_html; reject unrepresentable encodings; separate storage/projection versions; retain exact old stored source without inventing recovery; append hashes/provenance rather than a second live blob; allow empty raw edits; preserve sanitized-only delivery and network-free previews; validate durable receipts; retain current conservative conversion refusal; source export is a distinct inert text attachment.

Material setup/acceptance still outstanding: legal/source/asset retention approval for production use; actual Outlook/client preview procurement/evidence; qualified narrow VML/conditional grammar and its supported capability declaration; independent security assessment; full artifact/history/load/accessibility release evidence and final launch authorization. None blocks building the independent local source-truth path. This plan does not modify commercial scope or claim private pilot as a gate exception.

Alternatives rejected for this increment:

- Saving only sanitizer output: repeats the loss and cannot honor source roundtrip.
- Keeping two mutable source/sanitized canonical columns: introduces competing authority and stale acknowledgements.
- Automatically replacing code with derived output after save: hides transformation and overwrites newer local text.
- Treating HTTP 200 or returned doc_version alone as exact-source acknowledgement: creates forged/malformed/stale acknowledgement failure.
- Trusting client-supplied source/profile/hash/asset proof: avoids server authority and can expose wrong bytes.
- Broad VML/namespace/comment allowlists or placeholder reinsertion: preserves hostile payloads without a qualified email grammar.
- Silent VML removal plus “fidelity retained” warning: loses content in emitted output while implying usable correctness; preserve source and block unsupported delivery instead.
- Rendering original source directly in iframe/React diagnostics: expands execution/navigation/resource surface; preview projection is explicit.
- Baking private data/presigned URLs or UTM-mutated preview bytes into saved source: corrupts canonical references and expires distribution artifacts.
- Raising every API JSON limit or base64 source transport: enlarges unrelated attack surface and obscures true source-byte bounds.
- Recreating Monaco/handoff/history, raw-to-blocks permissiveness, MJML, browser formatting, remote-image fetch, provider sends or general infrastructure: outside the precise source-truth seam; sequence independently where still required.
- Fabricating lost legacy originals, changing frozen historical revision/artifact bytes, or declaring full TECH-032/Outlook acceptance: unavailable evidence cannot be invented.
