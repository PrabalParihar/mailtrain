# Membership lifecycle foundation

The next full-baseline foundation implements existing-member role changes/removal and atomic ownership transfer for REQ-002/003/004/057. Invitations, approved seat/plan catalogs and provider/collaboration recovery remain required follow-up work. No production/provider/account success is claimed.

Workspace administration uses signed-in Owner/Admin authority; bearer keys never manage memberships. Sensitive mutations require verified recent MFA in production, with actual nonnegative first+second factor ages no more than10minutes. Do not rely only on Clerk's reverification helper: its documented downgrade can allow first-factor-only identities. Native loopback local mode remains explicitly development-only and does not claim real MFA. [Clerk reverification](https://clerk.com/docs/guides/secure/reverification), [signed Auth factor ages](https://clerk.com/docs/reference/backend/types/auth-object).

Owner may manage existing memberships; Admin may manage Admin/Editor/Viewer members but cannot touch an Owner or grant Billing permission, which the role matrix does not give Admin. No ordinary role-change command grants Owner: only explicit transfer promotes an existing active target and atomically demotes the initiating Owner to Admin. An Owner may demote/remove another Owner only when an active Owner remains. No revoked membership can be revived by these commands. Transfer is distinct from subsequent leave/removal.

Owner/Admin/Editor count as editing seats; Viewer/Billing do not. Read-only current editing count and immutable before/after quantity evidence are local accounting, not a Stripe success. Positive seat-count changes require an approved capacity policy; until the catalog/entitlement slice supplies one, deny SEAT_POLICY_REQUIRED instead of assigning prices, grants or overages. Equal/decreasing seat-count transitions are allowed after ordinary authorization. Existing unapproved seat grants are never invented by localMode.

PostgreSQL serializes membership administration with an exclusive workspace row lock acquired BEFORE membership/shared authority locks. Ordinary private requests retain the previously verified shared workspace fence. Add immutable member UUID/created_at, version and revoked_at fields without changing the existing workspace/user uniqueness. Runtime loses direct INSERT/UPDATE/DELETE; a version-column row-lock privilege is retained solely for SHARE locking, with a trigger denying direct runtime mutations. Narrow NOLOGIN functions own changes and append immutable membership evidence; migration identity remains separate.

Removal/demotion that loses edit/delegation authority revokes that member's issued API credentials and cancels queued creation operations/releases their reservations exactly once; running work receives cancellation request and is not described as recalled. Local membership checks block removed identities across all private resources; global Clerk session revocation must not remove access to their other workspaces. Collaboration transport will separately enforce the same membership boundary when implemented.

Manager-only signed pages display user identifiers/role/status/version; no external identity lookup, invitation email or PII enrichment occurs. UI names the selected workspace, current seat impact and acknowledged versions, requires explicit destructive/transfer confirmation, fences stale workspace/read/write results and retains opaque command receipts across ambiguous acknowledgment/reload. Only definitive transactional CAS rejection releases a stale command receipt. A self-demoted or removed manager sees an explicit access-change result and can reload workspace selection; no fake acknowledgment is generated.
