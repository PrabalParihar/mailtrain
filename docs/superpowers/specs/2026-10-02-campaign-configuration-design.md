## Contract and policy
A draft campaign can change its name, exact immutable email revision and planned timing through one strict configuration command. Input: expected_version integer1..2147483646, name1..160, revision_id UUID, planned_timing:null or {local_time:YYYY-MM-DDTHH:mm,time_zone:supported IANA identifier,utc_offset:explicit ±HH:MM}. Unknown fields reject; callers cannot set provider, sender, audience, tracking, approval, state or digest. The saved timestamp includes UTC plus original local time/timezone/offset. It is planning data, not an accepted schedule. All actual schedule/send/approval gates remain closed.

Resolve the explicit offset to one UTC candidate, then verify every local minute/calendar part against Intl Gregorian/Latin-number/h23 formatting in the declared timezone. Reject invalid calendar dates, unknown zone and mismatch/nonexistent time. A repeated DST minute requires the user's explicit correct offset; both valid occurrences resolve distinctly. Do not infer timezone or offset from the machine, silently normalize dates, or claim future provider dispatch. Client shows planned timing and a sending-disabled notice; server remains authoritative.

Configuration updates lock the campaign after current withPrincipal authority, validate expected_version and same-tenant revision, derive the artifact hash, and retain the original audience/provider/sender/topic/tracking snapshot. Editing draft/review_pending resets to draft and invalidates any active review/approval metadata; other lifecycle states reject until explicit safe lifecycle handling exists. Approved/scheduled/dispatching/terminal mutation is not certified by this foundation. A current unchanged configuration is a no-op; stale base always conflicts. Keyed replay binds expected version as well as all settings, returns the original revision and creates no extra version; changed input under the same key conflicts. No auto-resubmit on conflict/navigation.

An additive campaign_revisions table stores exact immutable configuration snapshots per campaign/version, digest, actor, capture time and origin. Existing rows backfill only their current observed snapshot labeled migration_current; earlier versions are not invented. Future material changes append exactly one snapshot atomically with the base row, keyed receipt and audit. A restricted NOLOGIN history writer owns a forced-RLS trigger; runtime reads its own tenant but cannot directly insert/change/delete snapshots. A migration/operator authority can clean explicitly owned test fixtures. Tests distinguish those privileges. No destructive production migration or retention policy is adopted.

New GET campaign detail and signed campaign-bound configuration history expose name/version/revision/hash/timing/counts/digest/capture/origin metadata, never raw audience or secret configuration. Existing collection contracts remain compatible. Configuration POST uses campaigns:write; reads use campaigns:read under current role/key/workspace authority. Unknown/foreign campaigns or revisions do not leak content. Add generated OpenAPI/SDK contracts for every new command/read.

The editor holds the submitted form stable during an in-flight save, rejects repeated clicks synchronously, preserves fields after offline/errors and handles stale base with an explicit current-version reload. Lost acknowledgment retry uses the original unchanged payload/idempotency identity; reload reads authoritative saved settings with no automatic write. No-op protection prevents a freshly reloaded unchanged configuration from creating redundant revisions. Workspace-keyed mounting fences delayed receipts/history. Field and button labels distinguish planned timing, saved configuration, requested review, approved, accepted and delivered.
