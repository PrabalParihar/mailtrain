# Durable staged recipient ledger design — 2026-10-03

The full authoritative PRDv2 BaselineA, all65 requirements/all13 gates remain binding. REQ036 requires per-recipient dedupe identity, attempts and state history; TECH040–043 require complete approval before actual submission and no blind replay. The existing recipient assessment observes historical facts but creates no logical delivery. This independent reversible slice adds actual durable staged recipients/deliveries with a bounded worker and usable API/UI. Staging does not authorize sending or consume quota/frequency. Missing providers, approved manifests and spending decisions remain blockers for real dispatch. Continuous full-PRD development authorizes this technical foundation; no new commercial/provider/purpose policy is selected.

## Scope and alternatives

Recommended: one immutable staging ledger per immutable campaign configuration, independent of historical assessments, with deduped logical records and read-only empty attempt history. Reusing assessment rows would misrepresent observations as deliveries and cannot supply permanent dedupe identity. Implementing live dispatch now is blocked by authoritative sender/approval/client/budget dependencies; permissive fixture authorization is forbidden. This is one delivery-foundation slice, not a reduced baseline or final acceptance.

The staging command takes only `{expected_version,expected_digest}`. It verifies the current campaign's immutable configuration and frozen audience pointer/members using existing contracts. No new topic input is added: topic/purpose is not yet part of a complete approval manifest. No captured observation is promoted to send eligibility. Only draft/review_pending campaigns may create staging work. A configuration has one ledger; a different key with the same verified configuration returns that same resource. A later material configuration version creates a different ledger and never rewrites the old one. Cancelling a ledger does not allow recreation of the same configuration's logical recipients.

## Storage and identity

Migration037 after template036 creates `submission_ledgers`, `submission_ledger_jobs`, `campaign_recipients`, `deliveries`, `delivery_state_history`, `delivery_attempts`. Use existing workspace+campaign/configuration/revision/snapshot composite FKs, forcedRLS and current Owner/Admin manager checks with campaigns read/write plus audience:read API scopes. No Editor/Viewer/Billing recipient access. Immutable manifests pin configuration ID/version/digest, frozen email revision/artifact hash and snapshot ID/digest with sorted exact member array (max10000). Public projections omit HTML, addresses, credentials, personalization and arbitrary provider/error bodies.

Each captured member has one `campaign_recipients` identity unique by workspace/configuration/contact; contact IDs may be historical, so avoid a FK requiring a still-live contact. Delivery is unique per recipient. `logical_send_key` is lowercase64hex SHA256 of canonical JSON `[workspace,configuration_id,contact_id]`, derived by the server/database from immutable identifiers, never supplied by callers. Capture reason/locale/consent version stays immutable. Initial submission state is pending for captured-eligible members, otherwise skipped with the captured reason. Delivery outcome is independently unknown; authorization_issued is permanently false in this staging migration. No current eligibility/consent/locale approval is inferred.

Only staged pending→cancelled is currently writable; skipped/cancelled records cannot rewind. Runtime cannot insert reserved/submitting/accepted/uncertain/failed_permanent states, a provider message ID, authorization/payload evidence or delivery outcome. It cannot insert/update/delete attempt records. Accepted/uncertain state names may appear in strict future domain contracts, but no mounted method or runtime SQL authority can manufacture them. Future qualified migrations/authorizers must provide complete approval/provider/budget evidence before activating attempts. This slice does not simulate live provider acceptance in customer data. Immutable identity/history guards include DELETE/TRUNCATE and state/progress checks; history is appended by a narrow trigger role rather than arbitrary runtime writes.

Job states queued/running/completed/cancelled/failed have bounded atomic progress. `processed_count` equals exact committed recipient/delivery count, never exceeds total or increases over100 in a transaction. Counts `{pending_count,skipped_count,cancelled_count,accepted_count,uncertain_count,attempt_count}` are derived from actual rows; accepted/uncertain/attempt counts are0 under current admission gates. Cancelling queued/running/completed staging preserves rows/history, cancels only pending deliveries, and is idempotent. Cancellation/history/progress commit atomically. No charged ledger, frequency reservation or send outbox/event is written.

## Worker and authority

`processSubmissionLedgerBatch(tx,p)` runs under caller-owned BEGIN/COMMIT with a trusted development worker principal (no API key or local session); require current Owner/Admin authority. Lock one queued/running job FOR UPDATE SKIP LOCKED, recheck creator membership, API-key scopes/revocation/expiry and active workspace before each batch, then materialize at most100 sorted captured members. Database guards recompute pinned facts; caller flags do not establish authority. Revoked creator/key or changed campaign to paused/cancelled stops the remainder, preserves history and cancels staged pending rows. Current config edits do not rewrite admitted old manifest; worker uses its immutable captured configuration. No network call, Redis dependency or provider lease exists in staging. Loss before transaction commit leaves no partial progress; restart resumes durable PostgreSQL truth, duplicate workers remain harmless. CLI `scripts/run-submission-ledger.ts` is explicitly local-development/loopback only and refuses production; never start it against original data merely because it compiles.

## Exact public contracts

All mutations are internally keyed after current authority; root routes never wrap keyed twice. Optional X-Actor-Id must match current p.user; current authority applies before old receipt replay. UUID inputs canonical lowercase; digest lowercase64hex; counts0..10000. Strict known nonempty singleton query parameters, signed paging default25/max100 and filters bound to resource/actor/workspace/parent.

- GET/POST `/v1/campaigns/{id}/submission-ledgers`: list frozen metadata / create with exact expected version/digest, returns `{ledger:SubmissionLedgerView}` (POST201, including successful replay).
- GET `/v1/submission-ledgers/{id}`: `{ledger:SubmissionLedgerView}`.
- POST `/v1/submission-ledgers/{id}/cancel`: strict empty body, returns `{ledger:SubmissionLedgerView}`200.
- GET `/v1/submission-ledgers/{id}/recipients`: page of `StagedRecipientView`, each contains recipient/delivery ID, contact ID, captured locale/reason/consent version, logical key, submission state/outcome, updated time. Optional state pending/skipped/cancelled, signed filter bound.
- GET `/v1/deliveries/{id}`: `{delivery:StagedRecipientView}`.
- GET `/v1/deliveries/{id}/history`: page of `DeliveryHistoryView` (ID,delivery,state,outcome,reason,time).
- GET `/v1/deliveries/{id}/attempts`: actual page of `DeliveryAttemptView`; currently empty, no fake success and no create/update route.

`SubmissionLedgerView` fields: id,campaign_id,configuration_id,configuration_version,configuration_digest,revision_id,artifact_hash,snapshot_id,snapshot_digest,status,total_count,processed_count,pending_count,skipped_count,cancelled_count,accepted_count,uncertain_count,attempt_count,created_by,created_api_key_id,created_at,updated_at,completed_at,authorization_issued:false,dispatch_enabled:false. `StagedRecipientView` fields: id(recipient),ledger_id,configuration_id,delivery_id,contact_id,captured_locale,captured_reason,captured_consent_version,logical_send_key,submission_state(pending/skipped/cancelled currently),outcome:unknown,authorization_issued:false,created_at,updated_at. `DeliveryHistoryView` fields: id,delivery_id,submission_state,outcome,reason,recorded_at. `DeliveryAttemptView` is a strict redacted future schema with id,delivery_id,attempt_no,submission_state,request_started_at,accepted_at,error_class; no network attempt can exist under current SQL privilege/admission. Do not expose lease/provider credentials/raw error content.

## UI and recovery

Export `SubmissionLedgers({workspace,actor,role,id,version,digest})` and root mount alongside campaign recipient assessments. Owner/Admin can explicitly Stage recipient ledger, inspect progress/recipient/state/history/zero attempts and cancel staging. Other roles get no PII/mutation surface. Explain “Staged; sending unavailable”, captured versus current facts, and pending means unapproved work. Do not offer send, retry all, fabricated delivered or provider success controls. Show source configuration/version/hash and truthful counts. Empty/loading/error/reload/pagination/cancelled states and390px keyboard navigation remain usable.

Store exact original keyed create/cancel command before POST under workspace/actor/campaign scope, with strict finite bounded recovery and origin Web Locks for compare/write/ack (if unavailable, fail closed rather than claim cross-tab atomicity). Retain original command on network/401/malformed/ambiguous responses; changed version/digest/inputs cannot replace it. Shared coordinator synchronously blocks repeated clicks/mounted controls. Validate response identity before acknowledging. Fence actor/workspace/campaign changes and stale completion. For actual VERSION_CONFLICT409/DIGEST_CONFLICT409/STATE_CONFLICT409 from original create after keyed receipt check, explicit rejected-command dismissal may be implemented only with proven nonexecution and exact-receipt persistent classification; auth/unknown results remain held. No generic4xx clearing. Preserve original response replay even if source version changes later; current actor authority is still rechecked.
