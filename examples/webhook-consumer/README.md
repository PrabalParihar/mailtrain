# Persistent signed webhook receiver contract
This example accepts exact raw UTF8 body bytes before any JSON middleware. It checks the schema/event/workspace identity, fresh HMAC timestamp and declared current/overlap key version. The caller opens a PostgreSQL transaction, calls `acceptWebhookEvent`, commits, then replies2xx. Receipt and resource observation commit together. A retry returns a duplicate acknowledgment only when the existing consumer/event UUID also matches workspace and body hash. Older aggregate versions remain receipts and cannot replace a newer observation. Different topics use distinct scope identities.

Provision a separate receiver database and least-privilege identity, install schema.sql, and keep the consumer UUID, expected workspace UUID and current/previous signing-key inventory private. Do not use Lettercape's migration/runtime credentials. Bind inventory to this endpoint; accept at most one current and one unexpired prior version. Never key dedupe by timestamp, delivery attempt, signing version or process memory. An acknowledgment proves only this transaction; downstream external side effects need their own durable outbox/idempotency.

For n8n, preserve the Webhook node's raw binary request body and all signing headers. Put verification and the PostgreSQL receipt/effect transaction in a trusted receiver service invoking this contract; respond only after commit. Route committed observations into a separate durable n8n job with its own idempotency. Do not reconstruct bytes from parsed JSON or mark an asynchronous workflow enqueue as its final business effect. Use an owned fixture event and receiver state to verify retry, duplicate, rotation, reordering and crash recovery before enabling any target.

This is a tested reference contract and integration recipe, not an installed/exported n8n workflow. Owned local restart verification kills the test receiver only after its PostgreSQL receipt/effect commit and before an HTTP acknowledgment; a distinct fresh process accepts exact-byte retry with one effect, rejects identity conflict and preserves aggregate ordering. This does not establish actual account/runtime raw-body behavior, TLS/SSRF egress, production key/service setup, downstream integration, representative production restart/outage/load or replay/retention policy; those remain required. Outbound production delivery stays disabled.

The [official n8n Webhook documentation](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook) documents Raw Body and explicit response modes. Configure an explicit post-commit response; an immediate workflow-start response cannot establish this receipt/effect transaction. Validate the configured runtime preserves the exact bytes before using it.
